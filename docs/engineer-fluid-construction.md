# Engineer 水与岩浆施工

后续更新已加入[自动地基准备](engineer-ground-preparation.md)：缺失实心地基由
工程师按采样材料填补，当前存档版本为 7。下方版本 6 与 JAR 哈希是流体版本的历史记录。

## 使用

含水或岩浆的工程预览沿用同一份解析后的 Blueprint；普通方块先施工，
之后才注液，最后等待原版流体更新并核对目标。不会直接写入流动水来伪造完成。

- 默认分批存入水桶、岩浆桶；每次实际注液消耗一个满桶并归还一个空桶。
- 在确认工程前，看向 5 格内的源水，点击工程页“指定水源”，或执行
  `/squire project water source`。水源必须在工地 64 格内且位于工程区域外。
  之后只需存入一个空桶，侍从正常往返取水。建议准备可自然再生的 2×2 水池；
  单个有限水源被取走后会暂停，不会凭空补水。
- `/squire project water supplied` 恢复满桶交付模式。
- 带原生水域场地要求的模板可在确认前切换“人工水域”，或使用
  `/squire project water artificial`。明确标记的水域将变成开挖、永久石砖围护
  和水源目标，全部计入预览和材料。`existing` 切回沿用原有水域。
  人工水域不是自动适配任意地形；冲突、过大掩码或不安全围护会拒绝。
- 岩浆仅接受真实岩浆桶，不支持自动采岩浆。下界注水会拒绝。

水域设置在确认后冻结，避免中途更换几何或重复计算已支付材料。水源耗尽时
可恢复原指定水源，或补交满水桶后继续；要改源位置需取消并重新预览。

## 数据与结算

`ConstructionFluids` 保留源水/源岩浆、自然流动目标与含水方块。
`ConstructionPlan` 生成干态结构步骤；`FluidBuildExecutor` 在结构完成后执行
独立的注液步骤。含水台阶等对应一个实体材料操作加一个水桶操作。

`ConstructionCostPlan` v2 将流体操作与普通方块操作分开索引，避免同坐标覆盖。
满桶→空桶、空桶→满水桶均在工程托管库存内交换，保留材料来源归属。
容器不计等级损耗，也不生成额外空桶。原版自然水更新已经满足的目标不重复扣桶。
源水模式的未完成供料需求是一只可复用桶，不要求背包装下全部满桶。

每次取水/注液遵循持久化预写记录；世界操作、容器交换、操作结算和进度保存
完成后才清除记录。不确定的中断进入恢复待处理状态，不自动再次扣料或返桶。
已付费目标后来损坏不会免费重建。工程/蓝图存档版本升为 6，兼容读取旧存档；
旧工程继续使用已有的冻结快照，不由新资源替换。请勿用旧版本覆盖新存档。

## 安全与资源解锁

侍从必须有正常可达、安全且在原有施工距离内的站位；取水、注液都检查保护权限。
注液前检查目标占用、围护和岩浆周边可燃物。围护判定目前保守：底部和水平边界
需要完整密封面，不能证明安全的台阶/栅栏等组合仍会待适配。
许可范围以外的环境水域不自动扩挖，临时脚手架仍独立结算和清理。

取消工程不自动抽走已放置的液体或拆除永久围护。本次未扩展通用 Undo 的
流体传播回滚能力；拆除/撤销含水或岩浆工程前，应先人工排空液体，避免拆掉
围护后外溢。不要将普通方块的 Undo 当作完整流体事务回滚。

导入器保留水/岩浆的 level 和 waterlogged 属性，使用哈希绑定的
`vanilla-fluid-escrow-access-v4` 实测证据放行资源。既有流体限制解除不代表
所有相关 Tier 都安全：未映射外部方块、通路失败、漏液、火灾或物理更新
后结构变化仍明确隔离。KeepItLevel 的 MIT 来源与逐坐标替换报告保持不变。

验证入口：`M34FluidConstructionGameTests`（真实 NPC 与容器结算），
`M30CatalogQualificationGameTests`（750 个资源转换/施工顺序/物理更新审查）。
全库资格审查不是 750 座真实 NPC 工程的完整耗时测试。

只读资源审计：`python tools/audit_keepitlevel_fluids.py`，从转换后的 NBT 调色板
和场地元数据统计流体资源，单独排除仍使用旧冻结几何的六个兼容 ID。
因此旧蓝玻璃喷泉不会被误报为新水体施工已通过。
