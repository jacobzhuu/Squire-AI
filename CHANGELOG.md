# Changelog

All notable changes to Squire AI are documented here. Format based on
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning:
`0.1.0+mc1.20.1` during the RC line.

## [Unreleased]

### Fixed — the combat mode on the panel is the one he actually fights with

The behaviour page's "Fight" button read as inverted: picking *bow only* made him
charge in with a sword, picking *melee only* left him shooting. The labels and the
button's cycle were right; the **priority** inside `CombatStyle.prepare` was not.

- The "the weapon the player put in his hand wins" branch ran ahead of the chosen
  mode and never read it at all, so whatever happened to be in the main hand decided
  the fight. Worse, `equipForCommand` locked that weapon in *even when the swap had
  failed* — no bow, no arrows, or no melee weapon in the backpack — which is exactly
  when the hand holds the opposite of what the panel says. An empty quiver could
  therefore pin a "bow only" companion to melee permanently, arrows or not.
  The order is now: profession gate → physical reality (an empty quiver) → the mode
  the player picked → and only under *auto* does the hand-picked weapon decide.
- Weapon choice is gated by profession level on **every** combat path. Guard levels
  1–3 have not learned the bow yet, but autonomous retaliation
  (`AutonomyController`) and "go kill that creeper" (`AttackTargetExecutor`) called
  the ungated overload, so the limit only held on the escort path. A bow put into a
  low-level guard's hand is now holstered — he swaps to a melee weapon, or goes
  empty-handed rather than swinging a weapon he "cannot use".
- Picking a mode he cannot honour now says so instead of quietly meleeing: no bow,
  no arrows, or "the bow is a Guard Lv.4 ability". The mode is still remembered and
  takes effect on its own once the reason goes away, and the panel button reads
  "Fight: bow (locked)" meanwhile rather than claiming he is using one.
- Lv.2 "equipment awareness" no longer replaces a nearly-broken **bow** with a
  sword — it looks for another bow, or leaves the choice alone.
- Chat: negated phrases are matched before the words they negate, so 「别用弓」
  (*don't use the bow*) no longer sets bow-only via the substring 「用弓」, and
  「别用剑」 no longer sets melee.

### Added — professions: Guard and Engineer, levels 1 to 10

Implements `Squire_Profession_Progression_Design_v1`. A companion may take one
profession, earn profession XP by doing that profession's work, and be promoted a
level at a time by handing over materials. **Levels unlock behaviour, never stats:**
the whole Guard curve adds five hearts and at most +1.5 melee damage across ten
levels; everything else it buys is "he now knows how to use what you gave him".

- **Core** (`dev.squire.server.profession`): per-level XP bars (100 → 2800, 9400
  total), overflow capped at 25% of the next level, promotion materials from iron
  ingots up to a Nether Star / Beacon, and an ability registry of 22 entries.
  Promotion is never automatic — a full bar only earns a chat line.
- **Guard** unlocks, in order: swapping out a nearly-broken weapon (Lv2), threat
  scoring and a chase limit instead of "hit whatever is closest" (Lv3), the bow
  (Lv4), per-target weapon switching and a supply report (Lv5), raising a shield
  and eating before drinking a potion (Lv6), interposing between an attacker and
  its owner plus owner-emergency handling (Lv7), a Defensive/Balanced/Aggressive
  stance (Lv8), refusing to engage a Warden (Lv9), and dropping every low-value
  target the moment its owner is in danger (Lv10).
- **Engineer** unlocks a parametric blueprint: more templates and a wider footprint
  ceiling (9 → 48 across the ten levels), rotation (Lv3), per-region materials (Lv4),
  roof/foundation/window/entrance variants (Lv5), two and three floors (Lv6),
  mirroring and one optional module (Lv7), freely combined modules (Lv8), a compound
  outpost and saved blueprint presets (Lv9+). Shapes are still generated by
  deterministic Java — the model only ever picks parameters.
- **Anti-farming**: a kill only counts when the companion landed the last blow or
  dealt 20% of the target's max health; the same mob type decays to 5% after 50 kills
  in five minutes; a repeated boss pays a quarter; a repeated project decays to 10%.
  Material colour is deliberately not part of a project's identity, so re-skinning a
  house in spruce is not a new project.
- **Configurable**: every number above lives in `config/squire/profession.json`.
  A missing file is normal; a broken entry falls back on its own rather than
  producing half a balance table.
- New commands: `/squire profession`, `/squire stance`, `/squire supplies`,
  `/squire design`. The panel's companion page gained a profession line, an XP bar
  and a promotion indicator.

Existing companions are untouched: a save with no profession reads back as
"no profession", and every gate above is a no-op for a companion that never took one.

### Changed — the model is only offered the tools this companion can actually use

Profession and level now decide the tool catalog **before** it is serialized into the
request, not after the model has already picked something. Sending forty schemas and
then refusing half of them costs the same tokens and invites the model to improvise.

- One table (`ToolGate`) maps tool name → requirement, and both gates read it: the
  pre-serialization filter and the ToolGateway execution check. Two gates that
  disagree is the failure mode worth designing against, so there is only one table.
- Growth lines are exclusive. A Guard gets to *start* a fight (`guard.start`,
  `combat.attack_target`); an Engineer gets the parametric blueprint. Neither gets
  the other's. `guard.stop` stays available to everyone — start and modify may be
  gated, stop and cancel should not be.
- **Passive self-defence is not a tool permission.** Hitting back, eating, drinking a
  potion, equipping armour and following all live in the entity's own AI. An Engineer
  bitten by a zombie still fights back, and `combat.set_style` (bow vs. melee) stays
  available to everyone, because that governs *how* it fights, not whether it starts.
- Panel buttons, `/squire` commands and the chat FastPath do not pass through this
  gate, so nothing a player can do directly was taken away.
- An untrained companion keeps basic blueprints so the Lv.0 training milestone
  "build something once" is reachable; the multi-stage project and every parameter
  tool still require the profession.
- **An unresolvable companion is denied, not treated as a beginner.** A real beginner
  has a profile that says "no profession, Lv.0"; a missing profile means we could not
  work out which companion this is, which is not a reason to hand out permissions.
- Tools under `guard.` / `combat.` / `blueprint.` / `project.` / `build.` must carry
  an explicit entry, even when the answer is "everyone". "The author considered it
  and said yes" and "the author forgot" otherwise look identical, and the default is
  permissive. A test walks the live registry and fails on an omission.
- The prompt tells the model to name the level that unlocks a capability rather than
  emulating it with `setblock`/`fill`. That is advice, not enforcement — placing
  blocks one at a time is not mechanically distinguishable from hand-rolling a
  rotation, and the generic command tools remain owner-confirmed rather than removed.

### Added — the backpack's contents are visible in the panel

- The items page has a "Backpack" toggle that swaps the middle grid between the companion's
  own 36 slots and the worn backpack's contents, with arrows to page through backpacks larger
  than 36 slots. Items can be taken out and put in there directly.
- The two grids deliberately share one screen area: slot coordinates are fixed at construction
  time, so a backpack whose size is only known at runtime cannot get its own geometry.
  Writes go through the backpack mod's own storage, so filter, void and stack upgrades keep
  deciding what fits; a move that cannot be completed exactly is rolled back whole.

### Fixed — the nameplate no longer stacks two state tags

- The nameplate is assembled as `base name + [mode] + [progress] + activity`, and vanilla
  persists that assembled string as the entity's CustomName. A reloaded body had no base name
  and adopted the decorated string as its own, so the next mode change produced
  "阿福 [跟随] [巡逻]" — and another restart added a third tag.
- The base name is now stored separately in NBT, and the legacy fallback strips known
  decorations before adopting a persisted name.

### Changed — modded items are named in the player's own language

- Item, entity, enchantment and status-effect lookups now fall back to the game's own
  localized names. Missing-material lists print "还差 12 个 安山合金" instead of
  "create:andesite_alloy", and the companion understands modded items by the name printed in
  the player's inventory — without a hand-written table per mod.
- Curated aliases still win over the official name, so "火把" does not become "火炬". On a
  name collision vanilla wins, and the registry order breaks any remaining tie, so the same
  sentence always resolves to the same item.

### Added — the companion can wear a backpack

- The equipment column has a seventh slot for a worn backpack. It is independent of the chest
  armour slot, so carrying capacity and protection are no longer an either/or choice.
- A worn backpack is real extra capacity: the 36 main slots fill first and everything after
  that overflows into the backpack. Counting, capacity checks, material withdrawal and
  "fetch me one of those" all see the backpack's contents; taking something out of it pulls
  the stack back into a main slot first, because equipping addresses main slots by index.
- Tool, weapon and armour selection deliberately stay main-inventory only. The backpack is
  the overflow store, not his hands.
- The backpack item is rendered on his back, tracked to the client purely for that.
- Interop is dependency-free: the backpack's own item storage is looked up through
  porting_lib's item-storage table, whose types are all Fabric API. One reflective field read
  is the entire coupling, and without a backpack mod installed the slot simply accepts
  nothing. `BackpackCompat.Lookup` is an interface so the overflow, counting and withdrawal
  paths are covered by GameTests against a fake backpack.
- The worn backpack is persisted on the entity and in the world-level agent record, so it
  survives unloading, death and a re-summon.

### Fixed — the panel key brings the companion to you again

- Pressing the panel key (default K) now teleports the companion next to the player when
  he is more than six blocks away, not only when he is in another dimension. The panel
  opened at any distance, so the key looked broken whenever he was out of sight.
- Only the body moves: the movement mode is untouched and running work is not cancelled,
  so a stay order keeps its anchor and a builder walks back to the site.
- When no safe landing cell exists around the player (flying, in a boat, over lava) the
  companion stays put and says so instead of silently ignoring the key.

### Added — a sort button for the companion's backpack

- The items page has a "sort bag" button that merges stacks and packs them to the front of
  the 36-slot backpack, ordered by item id. The six equipment slots are never touched, which
  is exactly what an external sorter cannot guarantee on this screen.
- Merging uses `canCombine`, so enchanted, renamed and differently damaged tools stay apart.

### Fixed — Inventory Profiles Next no longer covers the panel header

- The squire panel now carries IPN's integration annotations. Without them IPN treats the
  companion's slots as a chest and injects four of its own buttons over the top-right corner,
  exactly on top of the mode readout.
- `@IPNPlayerSideOnly` keeps IPN's sorting inside the player's own 36 slots. Sorting the
  companion side would have shoved arbitrary items at the equipment slots (which refuse them)
  and would have silently reshuffled slots that are switched off on every non-item tab.
- The three remaining sort buttons are pinned directly under the right-hand button column,
  aligned to the same edges. `IpnCompatTest` intersects that strip against every occupied
  rectangle of the panel, so a future layout change cannot push them back onto a widget.
- The annotation types are declared locally (`org.anti_ad.mc.ipn.api`), so the mod neither
  depends on IPN nor changes behaviour when it is absent.

### Changed — fixed medieval buildings with per-part material palettes

- Replaced all five sparse built-ins with fixed, survival-scale medieval designs:
  a timber cottage, stone-and-timber lodge, framed storehouse, tall watchtower and
  fortified mine outpost. Their layouts now include deliberate beams, foundations,
  gabled roofs, windows and fixed functional blocks instead of generated boxes.
- A placement now stores independent material choices for foundation, frame, walls,
  floor, roof and windows. The panel has a dedicated material page with block previews,
  previous/next controls per part and a reset-to-default action; geometry never changes.
- Material families are explicit whitelists and may be extended by datapacks through
  `data/<namespace>/material_families/*.json`. Required derivatives are validated as a
  group, and stairs, ladders, slabs and logs retain their exact block states when the
  building rotates.
- Placement persistence is schema v2. Legacy variable-shape active sites are skipped
  instead of being resumed against incompatible fixed coordinates.

### Fixed — bow combat and player-like movement

- The first ranged shot now waits one full entity-sync tick after an automatic main-hand
  swap before starting item use, so the client receives the bow before the active-item
  flag and no longer drops the first draw animation.
- Arrow aim keeps the skeleton's body-targeting/gravity-compensation structure, but scales
  its lift from skeleton speed (1.6) to a fully drawn player bow (3.0). The old combination
  systematically sailed over targets; spread was not the main error.
- Follow combat stations, melee pursuit and persistent guard escort no longer rebuild a
  path every tick. Avatar position tracking is sent every tick as well, removing the
  close-range stop/start appearance.
- Follow movement now keeps its goal alive while the owner is walking, immediately
  refreshes a completed path instead of waiting out the remaining ten-tick cooldown, and
  only returns to the relaxed 6/3-block distance band after the owner stops.
- Automatic follow teleport no longer falls back to the owner's raw coordinates when no
  supported landing exists. Flying, gliding or falling owners therefore leave the
  companion safely on the ground until a valid landing becomes available; cross-dimension
  follow observes the same rule.
- Deep-water movement drives both the swimming flag and the `SWIMMING` pose every server
  tick. The avatar renderer now also applies the player renderer's whole-body pitch and
  translation, making the body horizontal instead of standing upright while paddling.

### Fixed — the panel's permission page did nothing in single-player

- `PermissionManager.has` checked `isAdmin` **before** the revocation set and returned
  `true` immediately. In single-player with cheats the player is always permission level
  4, so every node read as held: clicking a toggle really did record a revocation, but
  the tick never changed and nothing was ever gated. A whole page of dead switches.
- Explicit revocation now wins over the operator bypass — an operator holds every node
  **except the one they switched off themselves**. That is the same "a fine-grained node
  override wins" rule ADR-045 already claimed the manager had.

### Fixed — construction stalled on uneven ground

- `BlueprintBuildExecutor` treated a wall cell buried in terrain as "already occupied" and
  skipped it, reported `WORK_DONE`, and then `blueprintBuilt` read those cells as not
  matching the design — so the task sat in `VERIFYING` until it timed out. Any site that
  is not perfectly flat hit this; the player saw a few blocks go up and then nothing.
- `pendingClear` now also returns **cells blocked by something that is not part of the
  design**, so levelling the site happens in the excavation step where it belongs. It is
  all inside the blueprint's own footprint, which is the boundary ADR-038 draws; the
  excavation footprint gate was widened to match (`BlueprintManager.footprint`).
- `blueprintBuilt` additionally accepts a cell held by an **unbreakable** block (bedrock),
  the same way it already accepts a protected one. Refusing to accept it meant one
  immovable block could hang a whole building in `VERIFYING` with no way out but cancel.


### Changed — the companion fetches its own project materials

- **备料 now fulfils straight into the companion's backpack** and 交料 passes
  immediately. Routing materials through the player turned one sentence
  (「帮我准备一个矿井前哨站」) back into an errand. **保守 autonomy keeps the old
  hand-over route** — deciding whether materials pass through your hands is exactly the
  kind of thing that level is for (ADR-042 amendment).

### Fixed — he could not walk to a buried target

- `standableAdjacent` returns null for a block that is **buried** (all six neighbours are
  solid), and both build executors then fell back to pathing at the solid block itself.
  That path always fails, so the companion never took a step — he dug remotely from
  wherever he happened to be standing, and past 24 blocks reported `NO_REACHABLE_TARGET`
  instead. Since a shaft or a cellar is buried by definition, **every** excavation went
  down that road. New `approachPoint` walks him to the first standable spot above the
  target — the shaft mouth — which is what a person would do.


### Fixed — one body, one controller (ADR-048)

- **A task no longer erases the companion's standing order.** `AvatarEntity.moveTo`
  opened with `mode = MovementMode.IDLE`, so the first task that moved the body
  permanently discarded 跟随 / 待命 / 巡逻 and nothing ever restored it. After one job the
  companion would not follow, would not return to its anchor and would not patrol — from
  the outside, "他不干活了". The mode is now the player's standing order; a task only
  borrows the body (`taskDriven()`) and hands it back.
- **The move handle is released when it finishes.** It was set on every `moveTo` and never
  cleared, and two goals gated on `activeHandle == null`, so **patrol and the home routine
  could never start again** after the first task move.
- **The newest player command wins.** 跟随 / 待命 / 巡逻 / 回家 / 停下 — from chat *or* the
  panel — now cancel the running work, pause any project, and report what was put down.
  A work order (blueprint build, project start/resume) that targets somewhere outside the
  stay circle **gives up 待命 and says so** instead of vetoing the job the player just
  gave. 待命 still fences movement the companion starts by itself.
- **Excavating without a usable tool now fails honestly.** `ExcavateExecutor` counted
  unharvestable cells as *skipped*, so a companion with no pickaxe "finished" an
  excavation having moved nothing and then hung in VERIFYING until timeout. It now reports
  `PRECONDITION_FAILED`, and the project's 掘进 stage checks the tool up front and blocks
  with 「给他一把镐」. The 点灯 stage blocks the same way when he carries no torches.
- Two GameTests were depending on randomness added by earlier phases: the legacy patrol
  test asserted an emergent random walk (it now asserts that patrol actually starts), and
  the heal test derived its starting health from the damage formula, which the 皮实 trait
  perturbs.


### Added — playability phase 3 (projects: one sentence, six stages)

- **`Project → Stage → Goal → Task`.** 「帮我准备一个矿井前哨站」now decomposes into
  备料 → 交料 → 掘进 → 施工 → 点灯 → 验收. Stages compile into ordinary tasks on the
  ordinary scheduler; `ProjectCoordinator` adds exactly one rule — compile the next
  stage only while `scheduler.current(agentId)` is empty — so anything the player asks
  for preempts the project instead of competing with it (ADR-042).
- **Materials go to the player first.** 备料 fulfils into the *player's* inventory and
  交料 then waits until the companion actually carries the bill, listing exactly what is
  still missing. Without that step the newly un-banned hauling is never used and the
  chain "player is the source, companion is the labour" collapses. `PROACTIVE` autonomy
  is the only thing that skips it.
- **Blocking is a first-class state.** A stage waiting on a person is `BLOCKED` with a
  reason in plain words, not a stalled goal; a stage that fails **pauses** the project
  (`/squire project resume`) rather than deleting it and its progress.
- `/squire project [start <id>|pause|resume|cancel]`, the `project.start` tool (a
  template name only — the model never enumerates steps), a **工程** panel tab, and
  stage-boundary progress on the nameplate (`[施工 3/6]`) and in chat via
  `PlayerNotifier` (offline owners included). Nothing reports per tick.
- `LightUpExecutor` (`base.torch_up`) plants real torches from the companion's own
  backpack; `base.lights.set` only flips levers and presumes a base that already has
  redstone lamps. Placement rules are shared with the excavator's 照明 ability via
  `world.Torchlight`, so "a floating torch gets knocked off" is fixed in one place.
- Projects persist to `<world>/squire/projects.json`. Stage **states** are stored, not
  task ids (those change on restore); a stage that was running recompiles, which is safe
  because every stage condition reads the real world.

### Changed — playability phase 3

- `PanelState` is at version 3 (project name, state, stage list, blocked reason).
- `GoalRecord.Kind.PROJECT_STAGE` is tracked but **silent** on completion and failure —
  the project announces at stage boundaries, and two voices saying the same thing is how
  a chat log becomes noise.
- Two GameTests were leaving their profile-cached `FakePlayer` wherever a previous test
  dropped it (`M13`), or standing the companion on top of the owner so it swallowed the
  fulfilled materials before the haul stage could see them (`M16`). Both now pin
  positions explicitly.


### Added — playability phase 2 (roles, ability slots, growth, traits, autonomy)

- **Roles and ability slots.** Five roles (护卫 / 建筑师 / 管家 / 掘进工 / 探险家;
  农夫 listed and refused). A role's level-1 abilities are **basic** — every companion
  has them, role or not, and they cost no slot, so picking a role never removes
  anything it could do before. Level 2+ abilities are purely additive and must be
  equipped: 2 slots, 3 at role level 3, 4 at level 5, and the 4th only takes the
  current role's abilities. Unlocks are permanent across a role change, so carrying
  another role's ability costs a shared slot — that competition is the reason to
  summon a second squire (ADR-041).
- **Growth is milestones, never numbers.** `{40, 160, 500, 1400, 3500}` per track;
  every reward is an ability or a slot. Proficiency is credited in exactly one place
  — the scheduler's single terminal branch, and only for `COMPLETED` — so cancelled
  work pays nothing and a restart cannot double-count. Anti-idle: per-day soft cap
  with 20% overflow, **undo rebate** (undoing a build takes the proficiency back),
  already-correct blocks never counted, and hostile-mob kills only while the owner is
  online.
- **Advanced abilities that actually do something**: 集火 (attacks what you attack),
  护送 (guard radius ×1.5), 双倍工速, 通用建材 (narrow equivalence groups — planks for
  planks; the success condition accepts them too), 拆改 (clears a wrong block instead
  of skipping it), 工地物流 (fetches missing materials from a chest near the site via
  a dependent `container.withdraw` task), 照明 (torches from its own backpack after a
  dig), 深掘, 引路 (walks you to a recalled place).
- **Traits** — 1–2 rolled on first summon, never a contradictory pair, affecting
  **mechanics only**: retreat threshold, work rate, movement speed, damage taken.
- **Autonomy levels** 保守 / 标准 / 积极 (完全自动 defined and refused), stored per
  squire; an explicitly revoked permission node always wins over the level (ADR-045).
- `/squire profile | role [id] | ability [equip|remove <id>] | autonomy <level>`,
  a new **随从** panel tab, and a versioned `PanelState` packet replacing the five
  bare varints.
- New guide: `docs/guides/roles-guide.md`.

### Added — playability phase 2b (behaviour modes)

- **跟随** keeps a 3–6 block band instead of hugging the owner, and with 挡在前面 the
  companion positions itself between the owner and whatever is attacking them — falling
  back behind the owner instead once its own (trait-dependent) retreat threshold is
  crossed.
- **待命 is an area, not an anchor.** The companion roams freely inside `stayRadius`
  and walks back when pushed out. A task whose target lies outside the circle is refused
  with `OUT_OF_STAY_AREA` and an explanation, rather than silently doing nothing. The
  gate lives in `moveTo` and the area is stored separately from `MovementMode`, so it
  still holds for the second and later legs of a multi-step task.
- **巡逻 follows a route.** `/squire patrol add | list | clear` records waypoints (the
  square the *companion* is standing on); it walks them in order and stops at each for
  two seconds to inspect. `PatrolInspector` reports hostile mobs, ground dark enough to
  spawn them, and open doors — and says nothing at all when there is nothing to say.
  With no waypoints configured, patrol circles its anchor exactly as before.
- **回家收工.** Idle near home, the companion submits a `P7_IDLE` `home.routine` task
  of its own: swap in better armour it is carrying (装备维护) and stow leftovers in a
  nearby chest (囤积 trait or 积极 autonomy). The goal holds no business logic, so the
  routine is preemptable, timed out and logged like any other task. Default settings
  touch nothing.
- 挡在前面 / 装备维护 / 预警 are now `available` — no ability ships greyed out any more.
- `MoveHandle.errorCode()` is part of the body API; `MoveToExecutor` no longer flattens
  every failure into `PATH_NOT_FOUND` / `AGENT_STUCK`.

### Changed — playability phase 2

- `Task` gained a `WorkReport` that executors publish when they finish. The scheduler
  **reuses `executionState`** to hold the tick verification began, so an executor's
  counters are already gone by the time a task reaches `COMPLETED` — which is exactly
  when proficiency is credited. The accounting reads the report instead of
  pattern-matching executor internals.
- `AgentRecord.profile.autonomy` now stores an id (`standard`) rather than an enum
  name; `AutonomyLevel.byIdOrDefault` falls back to 标准 for anything unrecognised so
  a corrupt field can never promote a companion to a level that has not shipped.
- `M5CbpGameTests` positions its profile-cached fake owner inside its own test area;
  its assertions previously checked whatever cell the previous test left it standing on.

### Known gaps — playability phase 2

- **待命 changed meaning**: it was "return to within 2 blocks of the anchor", it is now
  "do not leave `stayRadius`" (8 blocks by default). Two GameTests encoded the old
  contract and were updated; `M3SecurityGameTests` used `setStayMode()` only to keep a
  body still and now uses `setIdleMode()`, because a distant navigation task is
  legitimately refused while on stay.
- The command page does **not** change with the role. Every advanced ability turned out
  to be a passive modifier rather than a new command, and greying out the basic buttons
  would mean "picking a role made him forget how to work" — see ADR-041.

### Added — playability phase 1 (blueprints, honest building, excavation)

- **Blueprints are data.** New `server/blueprint/` package: `Blueprint` /
  `BlueprintStep` / `BlueprintCodec` / `BlueprintRegistry`, five built-in shapes
  (`shelter_wood`, `shelter_stone`, `storage_shed`, `watchtower`, `mine_outpost`),
  and datapack loading from `data/squire/blueprints/*.json` — a new building is a
  JSON file, not a Java change. `/squire blueprint reload` re-reads them.
  `HouseTemplate` is not gone: it is now the constructor for the two shelters
  (ADR-039).
- **Materials really flow.** `BlueprintBuildExecutor` (`build.blueprint`) places one
  cell at a time, taking each block out of the companion's real backpack, and stops
  honestly with `INSUFFICIENT_ITEM` when it runs out. Steps are flattened to a
  per-cell final target first, so the bill of materials equals the shell that will
  stand — not the solid volume. `BillOfMaterials` discounts blocks already in place.
- **Excavation, bounded.** `ExcavateExecutor` (`build.excavate`) digs a blueprint's
  negative space with a real tool (durability written back, drops collected, dropped
  on the ground when full). Every cell is checked against the placement's own
  footprint before it is broken; an empty footprint forbids everything (ADR-038).
- **Ghost preview.** Particle outline sent to the owner alone — white/green/red by
  material status, smoke for cells that will be dug. No blocks, no entities, no
  client code (ADR-040).
- `/squire blueprint list | place <id> | status | fulfil | build | cancel | reload`,
  plus `blueprint.place` / `blueprint.build` in the model tool catalog. Placements
  persist to `<world>/squire/blueprints.json`.
- New guide: `docs/guides/blueprint-guide.md`.

### Changed — playability phase 1

- **Physical labour is re-scoped, not re-banned** (ADR-038, a bounded rollback of the
  narrowing below). The companion may now haul, build from a blueprint, and excavate
  **inside a blueprint footprint**. It still never mines ore, chops trees, farms,
  crafts or smelts in the wild; raw materials are still fulfilled with
  `minecraft.command.give`. `README.md` non-negotiable #6 and the system prompt were
  rewritten in the same change set, and the prompt wording is pinned by test.
- "帮我盖一个房子" no longer writes a whole house inside one tick with no
  materials. It now places a blueprint: outline first, bill of materials, then real
  construction. The old `SquireBuildService.buildHouse` path is retained unused as a
  reference.

### Fixed — playability phase 1

- `BuildStructureExecutor` had no `recoverySuccessCondition`: a restart mid-build
  failed the task with `SERVER_RESTARTED` while the half-built structure stayed in
  the world. It now rebuilds its condition from the persisted corners.
- `M5CbpGameTests` never positioned its (profile-cached) fake owner, so its
  "planning must not touch the world" assertions checked whatever cell the previous
  test happened to leave it standing over. Pinned to the test's own area.
- New GameTest class `M13BlueprintGameTests`: placement changes nothing, building
  really empties the backpack, running short stops honestly, optional cells are
  skipped without stalling verification, excavation never touches a cell outside the
  footprint, and the bill discounts what already stands.

### Added — playability phase 0 (groundwork)

- Permission toggles on the panel now persist across restarts
  (`<world>/squire/permissions.json`); previously every server restart silently
  reset them to the defaults.
- The agent store moved to schema v2: owner → record list, a direct
  `agentId → record` index, a `primary` flag (default command target) and a
  `SquireProfile` slot for future role/growth facts. One companion per player still
  applies. v1 worlds load unchanged; older mod builds fail closed on v2 files
  instead of eating the second record (ADR-047).
- Entity loading now resolves the record by agent id, fixing a latent bug where a
  second companion would have been discarded as "non-authoritative".
- Panel buttons are driven by a single table (`SquireActions`): id, label key,
  layout, click behaviour. All GUI labels moved to the lang files (new
  `squire.gui.*` keys, English and 简体中文). First tests covering the GUI seam
  (`SquireActionsTest`) (ADR-046).
- Armour-set buttons call a typed equip path instead of re-parsing their own
  Chinese labels.

### Fixed — playability phase 0

- PATROL is no longer silently downgraded to IDLE across dismiss/resummon,
  restart, or cross-dimension teleport. The three restore paths collapsed into one
  (`AvatarEntity.applyMovementState`), and a GameTest pins the behaviour
  (`patrolModeSurvivesDismissAndResummon`).
- New GameTest class `M12StoreMigrationGameTests` covers the v1→v2 agent-store
  migration, future-version fail-closed, corrupt-row isolation and
  profile/primary round-trips.

### Changed — narrowed companion interaction model

- Physical companion work is now limited to follow/stay, guard/stop-guard, and
  owner rescue/healing. Mining, crafting, smelting, hauling, equipment changes,
  ordinary building, automation, and materialized CBP tools are no longer exposed
  to model planning; legacy executors remain loadable for existing task state.
- “Give / gather / craft / smelt” item wording now converges on the bounded,
  registry-validated `minecraft.command.give` path. That safe fulfilment path is a
  default player permission even while optional admin commands are disabled.
- Fill and setblock tools now compile directly to vanilla `/fill` and `/setblock`
  after confirmation and protection checks; command edits no longer advertise or
  create per-block Undo history.
- Added one command execution boundary: commands up to 256 characters run inline;
  longer commands execute through a protection-checked temporary command block,
  preserve the Java-bound `@s`, and restore the original block in `finally`.

## [0.1.0] — v1.0 Release Candidate (2026-08-26)

Milestone M0→M6 implementation of `docs/IMPLEMENTATION_SPEC.md`.

### Added — core
- Companion avatar bodies (server-authoritative entities) with follow/stay/home/
  dismiss control, owner binding and persistence across restarts (M1).
- Conversation pipeline: FastPath intent shortcuts before LLM calls; provider-
  independent protocol (`AgentRequest`/`AgentResponse`); async-only provider I/O
  on a dedicated executor (M1/M2).
- Perception → structured function-calling runtime with typed tools, task graph
  (priority preemption, bounded retries, timeout), and server-side goal
  verification — the model never declares completion (M2).

### Added — security & world editing (M3)
- Permission nodes, capability scopes (dimension/region/maxImpact/quota),
  risk policy gates, quota ledger, audit log (`audit.jsonl`), killswitch.
- WorldEditor: preview → capability re-validation → protection check → undo
  journal → frame-budgeted writes → verify. Refuses when not journalable.
- Structured command compiler: give / effect / summon-safe / teleport as typed
  intents compiled through Brigadier; whitelists shared with CBP.

### Added — extension platform (M4)
- `squire` entrypoint: third-party tool/sensor/task providers with trust levels;
  untrusted + write-shaped = denied regardless of claimed annotations.
- Minimal self-built MCP client bridge (JSON-RPC over HTTP/SSE-free stdio-free
  transport set): data-only results, async settlement, per-server trust store,
  timeouts that can never block the server thread.

### Added — automation & materialized CBP (M5)
- AutomationGraph: trigger/condition/node graphs owned by players, TTL-bounded,
  default-off, deduped firings, restart recovery with re-primed region state.
- CBP materializer: explicit spec → workspace containment → owner confirmation →
  capability → inert placement → armed verify-or-undo; persistent registry;
  honest refusal when blocks cannot be restored after restart.

### Fixed — acquisition planning (post-RC)
- `task.acquire`/`crafting.craft` refused bare item ids (`"torch"`), which models
  commonly send — the planner now applies the implicit `minecraft:` namespace and
  NO_RECIPE refusals list every obtainable item so the failure is actionable.
  Regression unit tests added.

### Fixed — avatar placement & follow (post-RC)
- Summoning while looking down buried the body in the ground (the spawn offset
  included the view pitch). Placement is now horizontal-only and snapped to a
  standable column, falling back to the owner's own tile; regression GameTest
  added (`summonLookingDownNeverBuriesTheBody`).
- Follow now engages past ~4 blocks instead of ~5 (stop distance unchanged).

### Changed — avatar appearance
- Default look is the classic player model in its Alex form (slim arms), using
  the vanilla alex texture referenced at runtime from the `minecraft` namespace;
  no Mojang asset is bundled.

### Added — real inventory, logistics, guard and location memory (playability C/D/E)

Work packages C, D and E of `docs/PLAYABILITY_REMEDIATION_PLAN.md`.

- `AvatarInventory` is now the only write path for the companion's items: 36 main
  slots plus both hands and four armour slots, NBT/enchantment/durability preserved
  on every move, capacity precheck, and snapshot/restore for transaction rollback
  (ADR-029). Equipment drop chances are zeroed so death cannot duplicate gear.
- Gathering mines with the REAL tool from its real slot and writes the wear back
  there; a block that needs a tool the agent does not have is refused instead of
  destroyed for zero drops. Drops that do not fit stay in the world.
- `inventory.equip` / `inventory.unequip` / `query.equipment`: equipping MOVES the
  item, never copies it.
- Container logistics — `container.deposit` / `withdraw` / `transfer` / `sort` /
  `inspect` and `inventory.pickup_nearby` — run as two-phase transactions behind one
  validated `ContainerAccess` seam (double chests, reach, chunk load, protection),
  each submitted with a baseline-anchored goal condition (ADR-030).
- Smelting uses a REAL furnace / blast furnace / smoker and takes the output the
  vanilla block entity produced; crafting requires a real crafting table for recipes
  that do not fit a 2×2 grid. Neither is ever auto-placed (supersedes ADR-022).
- Long-term guard is a persistent `GuardPolicy` on the AgentRecord driven by a local
  combat runtime, not a 24000-tick task; it lies dormant while the owner is offline
  and ends only when the player says so (ADR-031).
- `aid.owner` heals the PLAYER with real items from the companion's backpack through
  each item's own effect path — splash potions are really thrown — and reports
  `INSUFFICIENT_HEALING_ITEM` rather than conjuring one. `heal.self` likewise runs
  vanilla `finishUsing` instead of a flat HP grant (supersedes ADR-021).
- `LocationMemoryStore`: dimension-aware HOME/WAREHOUSE/FARM/MINE/CUSTOM memories with
  the six `memory.*` tools, "这里是仓库" / "仓库在哪" / "上次矿洞在哪" / "把矿放回仓库"
  FastPath phrases, and ambiguity reported as candidates instead of guessed (ADR-032).
- Ordinary gathering, single-block break/place and every container write now consult
  the same `ProtectionAdapter` as WorldEdit and CBP, refusing with `PROTECTED_REGION`.

### Fixed — task timeout accounting

- A task's timeout counted from the tick it was QUEUED, so anything waiting behind a
  slow dependency burned its whole budget before it ever ran. With real furnace cook
  times this timed out every craft queued behind a smelt. The budget now starts when
  the task starts.

### Added — selection, confirmation replay and durable undo (playability F)

Work package F of `docs/PLAYABILITY_REMEDIATION_PLAN.md`.

- `SelectionService`: persistent, per-player, per-dimension region selection via
  `/squire selection pos1|pos2|show|clear` (bare `pos1`/`pos2` use the block you are
  looking at, and always echo the resolved dimension, bounds and volume). Bulk edits
  reference the server-owned selection; the model never emits coordinates.
- High-risk operations are now durable `PendingOperation` records carrying the
  CANONICAL arguments and the preview the player saw. `/squire confirm <id>` replays
  that stored operation once on the server thread — the player never repeats their
  sentence, and altered arguments cannot ride on a confirmation given for different
  ones (ADR-033). Added `/squire deny <id>` and expiry sweeping.
- Previews now say what a player needs to decide: tool, dimension, region and volume,
  cells that would really change, materials, entities and containers inside, and the
  undo size.
- Undo is persisted to the world save and survives restarts, restoring block states
  with their properties and BlockEntity NBT (chest contents included). It re-checks
  protection, and refuses to overwrite cells changed after the fact until the player
  confirms with `/squire undo <id> confirm`. Added `/squire undo [id]` and
  `/squire undo list` (ADR-034).
- `build.structure`: ordinary building (SOLID / HOLLOW / WALLS / FLOOR) that spends
  REAL blocks from the companion's backpack, checks protection per cell with an
  explicit STOP/SKIP policy, and is undoable like any other edit.
- Scoped capabilities are re-validated on every write batch and revoked as soon as the
  operation completes, fails or is cancelled.

### Fixed — bulk edits aborted on their first batch

- The new per-batch capability re-check compared the BATCH size (256) against the
  operation's `maxImpact` (its total cell count), so every bulk edit stopped before
  writing anything. It now checks the operation's total planned impact.

### Added — player-created automation that controls real redstone (playability G)

Work package G of `docs/PLAYABILITY_REMEDIATION_PLAN.md`.

- `AutomationCompiler`: named templates (today `NIGHT_LIGHTS`) compile into validated
  graphs. Triggers, node kinds and the tools a node may drive are all whitelisted — no
  high-risk world/command/CBP tool is reachable from an automation, so a long-term
  graph cannot become a way around confirmation. Validation covers the node cap, a
  minimum trigger interval, tool existence and cycles unpaced by a WAIT node.
- "每天晚上在基地开灯" works from chat with no LLM: it previews the triggers, action,
  location, validity and permissions, and one `/squire confirm` registers the graphs
  (ADR-035).
- `base.lights.set` flips REAL levers within a bounded radius of the remembered base,
  with the neighbour updates vanilla performs, so the lamp lights from an actual
  redstone signal. No command blocks, and no faked `lit` flag — setting that directly
  would be reverted by vanilla's next scheduled tick. Every write passes protection
  and lands in the undo journal.
- Recurring automations now run INDEFINITELY until paused or removed; one-shot graphs
  may still set an explicit TTL. The engine's enabled flag is persisted, so an operator
  enables automation once rather than after every restart. Legacy files carrying the
  old implicit two-week TTL are migrated once, with a log line.

### Fixed — enabling automation before recovery could delete every automation

- Persisting the enabled flag made `setEnabled` save, and saving before `load()` wrote
  an empty graph list over the file — so enabling automation after a restart wiped the
  player's automations. Saving is now suppressed until the engine has loaded.

### Added — real command-block projects, only when asked for (playability H)

Work package H of `docs/PLAYABILITY_REMEDIATION_PLAN.md`.

- `CbpIntent` gates the only feature that leaves command blocks in a world. Only an
  explicit ask ("命令方块 / command block / 可编辑 / 教学 / 红石装置") enters the flow;
  outcome-on-a-schedule requests are steered to the AutomationGraph and told so, and
  anything ambiguous asks the player instead of writing the world (ADR-036).
- `CbpPlanner` compiles whitelisted templates — a real day/night controller and an
  editable pulse/repeating teaching device. Every baked command is generated in a
  shape `CbpCommandPolicy` allows and re-validated, so the model cannot smuggle in a
  raw command; it only picks a template and an anchor.
- `CbpSpec` now supports the parts a real device needs: a small support-block
  whitelist (daylight detector, redstone lamp, lever, sign, stone), orientation, the
  conditional flag and sign labels. Support blocks may never carry a command.
- New tools `cbp.preview_project` (read-only), `cbp.plan_project` (previews and asks
  for confirmation, writes nothing) and `cbp.materialize_project` (places an
  already-confirmed plan). Placement remains one code path, reachable only after a
  real confirmation from the owning player.
- A project's undo journal is owner-attributed and persisted, so `/squire cbp remove`
  restores the exact prior blocks after a restart. Capabilities are revoked as soon as
  placement finishes.

### Fixed — support blocks were placed as command blocks

- `blockFor` fell back to COMMAND_BLOCK for any unrecognised type. Once templates
  contained detectors, lamps and signs, that silently turned each of them into a
  command block. It now resolves through the registry and refuses unresolvable types.

### Added — external tool and MCP result loop (playability I)

Work package I of `docs/PLAYABILITY_REMEDIATION_PLAN.md`.

- `PendingExternalCallRegistry`: every in-flight external call now has an owner, a
  tool and a deadline. A tick sweep turns an unanswered call into a structured
  `MCP_TIMEOUT` so a turn can never wait forever; a disconnect fails everything in
  flight for that server at once; a result arriving after its call already timed out
  is ignored rather than reopening a settled question (ADR-037).
- `McpCircuitBreaker`: after repeated failures a server's circuit opens and calls fail
  fast with `MCP_CIRCUIT_OPEN` instead of costing a full timeout each. A cooldown then
  admits one probe call; success closes the circuit again.
- `ExternalResultSanitizer`: bounds payload size, string length, nesting depth and
  collection width, and redacts fields whose names look like credentials (`token`,
  `apiKey`, `authorization`, `password`, …). Everything removed leaves a visible
  marker. It runs on the way into observations, so chat, the audit log and the model
  prompt all see the same bounded view.
- `ResultRenderer`: players get one readable line
  (`factory:machine_status: status=running, energy=812`) instead of raw JSON, while the
  full structured data still reaches the next model turn.
- `config/squire/mcp.json` plus `/squire admin mcp list|reload|status <server>`:
  operators deploy and reload MCP servers without writing Java. The file is the only
  place a server address or launch command is accepted, and it names a `trustKey` into
  the existing trust store rather than carrying trust itself. A broken entry is skipped
  with a reason; the healthy servers still load and startup is never blocked. The
  shipped example has every server disabled.

### Changed — MCP guide states the real protocol surface

- The guide now names exactly what is implemented (newline-delimited JSON-RPC over
  STDIO, plain POST over HTTP, `initialize`/`tools/list`/`tools/call`) and what is not
  (SSE, `Content-Length` framing, resources/prompts/sampling). Claiming broader support
  sends operators to debug their own servers for a limitation of ours.

### Added — real LLM connectivity (post-RC, §23)

  endpoint (OpenAI, vLLM, Ollama compat layer, gateways). Fully async JDK

  masked `/squire admin llm` inspector and `reload` subcommand. Players never
  supply keys.
- The model's tool calls still flow through the strict JSON turn contract and
  every ToolGateway stage; the provider itself stays a dumb text adapter.
